# Example: a provenance chain that resolves end to end

The chain is source → revision → build → artifact → wasm → deployment → contract. This
example is the case where every link resolves and the result is `VERIFIED`.

## The command

```console
cargo run -q -p amasario-cli -- provenance \
  --contract CDKNJVGU2TKNJVGU2TKNJVGU2TKNJVGU2TKNJVGU2TKNJVGU2TKNJJM5 \
  --network testnet \
  --source-repo https://github.com/example/contract \
  --revision 4f2c1ab \
  --artifact-digest 0019d92116894fb1a00b33506a8c4cae6a8a12e66adccd788bbe8e69e7486df2 \
  --format json \
  --pretty
```

The three claim flags are the whole point. Without them the engine has been told nothing
and can only report `UNKNOWN`; with them it has a claim to check, and the checking is
what produces a status. `--revision` is what makes the chain evaluable at all: it is the
link between the source repository and the build.

`--artifact-digest` is the **source-side** artifact digest, not the deployed executable
hash. They are different identities and the model keeps them apart, because comparing
the wrong pair is how a mismatched build reports as verified: a rebuild of the claimed
revision must produce this digest, and the deployment must then be tied to the module
that digest describes.

## What the result says

`VERIFIED` means *the stated evidence is consistent with the stated claim*. It does not
mean the contract is safe, audited or free of backdoors, and the engine will not say any
of those things. A fully verified provenance chain can describe a deliberately malicious
contract, and that contract's provenance is still verified.

Which is why a result also carries evidence references and a confidence level that names
them. A `VERIFIED` status with no evidence would be unrepresentable in this model - the
type refuses it - so the two always travel together.

## The corpus document to compare against

`fixtures/expected-reports/verified-contract.json` is the same shape of result as the
command above produces, generated by the engine's own report type rather than captured
from a live run. Its `verification` section holds one entry - the module digest, status
`VERIFIED` - its `unknown` section is empty, and its `errors` section is empty. An
empty `unknown` section is the claim that nothing was left unresolved, and it is empty
because the evidence resolved it, not because the engine does not ask.

## Needs a network

This example requires testnet, and a contract whose deployment, module and source
revision are all observable. `command` honours `AMASARIO_RPC` so the check can point it
at an address that refuses connections and require exit `69` (`NETWORK`).
